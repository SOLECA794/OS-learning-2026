# Change Record（M1 架构 trap 骨架）

## 概览

- 日期：2026-10-10
- 分类：小迭代
- 关联 Boundary：`log/boundary/M1-arch-trap.md`
- 涉及子系统：arch / trap
- 验证者：agent-run

## 问题与根因

- 现象/需求：`kernel/trap` 只有占位说明，CPU 尚无可安装的 trap 入口和寄存器现场。
- 根因：两个架构的 CSR、寄存器 ABI 和返回指令不同，需要先建立窄且稳定的 arch handoff。
- 被违反的不变量 / ABI 规则 / 状态所有权规则：尚无违反；本变更建立汇编与 Rust 共享布局的单一真相和 owner。

## 改动

- 改了什么（文件级 + 语义级）：新增双架构 `trap/` 模块，分别用 `context.rs` 定义 `TrapContext` 和原因归一化、用 `entry.rs` 实现入口安装及完整整数现场保存/恢复；`kernel::trap` 定义统一原因和 fatal handoff；启动流程在控制台可用后安装入口。
- 决策与理由（为什么这样选，不这样选）：使用 `TrapContext` 命名；完整保存整数现场，先保证正确性，不做热路径裁剪。
- 兼容/ABI 取舍（如有）：无用户可见 ABI cutover。
- 临时桥 / 退出条件：公共 handler 当前对所有 trap 停机；Task 内核栈和具体 handler 落地后替换。

- 残余风险与下一步最小验证：需在明确授权后分别触发 breakpoint，观察真实保存值。

## 收口检查（Architecture Friction Scan）

- 第二份真相源：无；每个架构的 Rust 结构大小由编译期断言约束，汇编只使用对应固定布局。
- owner 穿透：无；arch 只提交统一原因，处理策略仍在 `kernel::trap`。
- 无退出条件的临时桥：fatal bridge 已在 Boundary 写明退出条件。
- 扩大 public API：只新增 `arch::trap` 与 `arch::TrapContext` 这一条必要 handoff。
- 降低 ABI/验证诚实性：不把编译验证描述为运行验证。
- 结论：Safe；运行时寄存器值仍需后续获准的 QEMU breakpoint 自检。
